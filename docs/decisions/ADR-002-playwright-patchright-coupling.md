# ADR-002 — playwright·patchright 버전 결합을 파일 제약으로 강제한다

**상태**: 승인됨 (2026-09-28)
**관련**: PY311-001, `requirements.txt`, `scripts/test_requirements.py`

## 맥락

`requirements.txt:23` 은 이 규칙을 산문으로만 적고 있다.

> ⚠ playwright 와 patchright 는 버전이 함께 움직여야 한다(둘 다 1.62.x) — 한쪽만 크게 올리지 말 것.

`patchright` 의 PyPI 설명은 "Undetected Python version of the Playwright testing and
automation library" 이고, 2026-09-28 실측에서 두 패키지의 1.6x 마이너 라인은 완전히 같다
(playwright 1.60/1.61/1.62/1.63, patchright 1.60/1.61/1.62/1.63). 결합은 실제로 성립하는
관계다. 문제는 **규칙이 파일 제약이 아니라 주석이라는 것**이다.

`playwright>=1.62` 와 `patchright>=1.62` 는 상한이 없다. 따라서 해석기에 따라
`playwright==1.99.0` + `patchright==1.62.5` 같은 분리는 파일이 막지 못한다.
오늘 두 패키지가 1.63.0 으로 함께 올라간 것은 **해석기가 그렇게 골랐기 때문**이지
파일이 강제한 결과가 아니다.

## 결정

두 줄에 **바이트 동일한 제약식**을 준다. 하한 `1.62` 는 기존과 같고,
상한 `<1.64` 은 2026-09-28 실측에서 두 패키지 모두 1.64 가 PyPI 에 없기 때문에 넣었다.

```
playwright>=1.62,<1.64
patchright>=1.62,<1.64
```

그리고 `scripts/test_requirements.py` 에 두 검사를 둔다.

- `test_playwright_has_upper_bound` — 상한 부재를 막는다. (`test_scrapling_has_upper_bound` 와 같은 논리)
- `test_playwright_and_patchright_constraints_identical` — 앞으로 한쪽만 고치는 변경을 막는다.

## 이 결정이 강제하는 것과 **안** 하는 것 (정직한 한계)

**강제한다**
1. `playwright` 에 **버전 상한**이 있다 — 없으면 1.64 출시에 patchright 를 두고 독주한다.
2. 두 줄의 **제약식이 바이트 동일**하다 — 한쪽만 고치는 변경을 CI 가 먼저 잡는다.

**강제하지 않는다**
- **해석된 버전의 동일성.** 2026-09-28 실측으로 이 체크아웃의 `.venv` 는
  `playwright 1.62.0` + `patchright 1.62.3` 이었고, **둘 다 `>=1.62,<1.64` 를 만족한다.**
  제약식이 같아도 해석된 패치 버전은 다르다. patchright 만 1.60.1 / 1.61.2 / 1.62.3 같은
  추가 패치 릴리스가 있고, playwright 는 1.60.0 / 1.61.0 / 1.62.0 처럼 매 마이너 1개다.
- **마이너 라인 추종 자체.** 그건 upstream 의 릴리스 규칙이지 이 파일이 만들 수 있는 게 아니다.

정확히 같은 버전을 강제하려면 lockfile 가 필요하고, 이 저장소에는 lockfile 이 없다
(`.gitignore` 도 CI 도 lockfile 을 만들지 않는다 — `checks.yml` 은 매번 새로 해석한다).
그러니 "결합을 보장한다" 고 말하지 않는다. **"한쪽만 바뀌는 변경을 막는다"** 고 말한다.

## 이유

**대안 1 — 주석만 고친다.** 기각. 결합이 계속 장식이다.
`CONTINUITY-REV-001` 가 이미 "증명 못 하는 규칙은 조용히 통과하는 장식이라 두지 않았다" 고
승인했다. 산문 규칙은 조용히 통과하는 게 아니라 **조용히 깨진다** — 깨진다는 게 더 나쁘다.

**대안 2 — 두 줄을 하나로 합친다.** 기각. pip 은 이 관계를 표현하지 못한다.
`patchright` 는 `playwright` 에 의존하지 않는다(양쪽 METADATA 에 상호 의존 없음 — 2026-09-28 실측).
합치면 존재하지 않는 의존을 만들어낸다.

**대안 3 — 상한 없이 동일 제약식만 둔다.** 채택하지 않음, 근거는 아래.

**대안 4 — lockfile 를 도입한다.** 기각, 범위 밖. lockfile 는 이 저장소의
"가벼운 설치"(ADR-001)와 정면으로 충돌한다 — 해시 고정 파일이 늘고, 해석이 아니라 고정이 된다.
이 결정의 범위는 파일 안에서 끝난다. lockfile 가 필요해지면 그건 별도 결정이다.

### 대안 3 을 기각하는 근거 (인용이 아니라 사실)

상한이 없으면 `>=1.62` 인 두 줄은 1.64 가 나올 때
`playwright 1.64.x` + `patchright 1.63.x` 로 **조용히 갈라진다**. 상한은 그 분할 지점을
지금 미리 못 박는다. 상한이 없으면 "두 줄이 지금 같으니 계속 같겠지" 가 추측이 되고,
상한이 있으면 "<1.64 는 두 줄에 함께 적용된다" 가 파일의 사실이 된다.
**그래서 상한은 결합 장치가 아니라 브레이크다.** 이 구분이 2026-09-28 독립 리뷰
(findings: "결합 강제 주장이 과장") 로 교정됐다.

## 상한 `<1.64` 를 **측정**해서 넣은 이유

추측으로 정한 숫자가 아니다. 2026-09-28 에 pypi.org JSON API 를 읽어 확인했다 —
두 패키지 모두 1.63.0 이 최신이고 1.64 는 존재하지 않는다.
`shasum` 처럼 **해시로 고정할 수 없는 값**(시간에 따라 움직이는 값)이므로,
파일 제약으로 못 박되 그 값이 언제 낡는지 계약(PY311-001 UNVERIFIED)에 적어 두었다.

## 결과

- `requirements.txt:23` 주석의 "(둘 다 1.62.x)" 는 **재해석 결과와 거짓말이었다**(둘 다 1.63.0).
  이 결정으로 주석을 허용 범위 서술로 고친다.
- 이 결정은 CI Python 3.11 축을 닫는 작업(PY311-001)과 같은 세션에서 나왔지만 **다른 문제**다.
  분리한 이유는, 두 축을 한 테스트에 묶으면 어느 쪽이 깨졌는지 다음 세션이 구분 못 한다.
